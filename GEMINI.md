# GEMINI.md — instructions for Gemini CLI and Google Antigravity

@AGENTS.md

The import above is the full shared project guide (architecture, commands, rules, testing, migrations). Everything below is specific to **Gemini CLI / Antigravity**. If the two ever conflict, the stricter rule wins; fix the discrepancy in `AGENTS.md`.

## How to work in this repo

1. **Orient first.** Read `AGENTS.md` §3 (repo map), §4 (architectural rules), §8 (scope discipline). Then open the neighbouring module and its test before writing code.
2. **Plan, then implement.** For anything beyond a small fix, produce a short plan (files to touch, migration needed?, permissions added?, tests to add) and get confirmation before editing. In Antigravity, capture this as a plan/task artifact and keep it updated as you work.
3. **Verify before claiming done.** Run the full check set in `AGENTS.md` §2 and report the actual output, including anything you could not run.

## Commands and environment

- Everything runs through `uv`: `uv run pytest -q`, `uv run ruff check .`, `uv run alembic upgrade head`, `uv run --with pyright pyright`. Do not use bare `python`/`pip` or create a new virtualenv; `.venv` is managed by `uv`.
- Use a throwaway database for migration checks (`DATABASE_URL=sqlite+aiosqlite:////tmp/check.db …`) so no `.db` files are created in the repo. Never commit `*.db` or `.env`.
- If you run the server or a terminal command that blocks (uvicorn `--reload`), run it in the background/separate terminal and stop it when finished.
- Antigravity browser agent: the API is a backend with Swagger UI at `http://127.0.0.1:8000/docs`. You may use it to exercise endpoints manually, but it requires `DEBUG=true`, `SEED_DEMO_DATA=true`, a dev bearer token, and the `X-Tenant-ID: demo-tenant` header (see `AGENTS.md` §2). Automated tests remain the source of truth for correctness.

## The `.agents/skills/` library

`.agents/skills/` (an Antigravity skills collection, gitignored) contains many generic skills. Treat them as optional reference:

- Potentially useful here: `backend-architect`, `api-design-principles`, `async-python-patterns`, `backend-security-coder`, `architecture-decision-records`, `code-reviewer`, `cqrs-implementation`.
- Not applicable to this repo: blockchain, C/C++/C#, Airflow, Angular, ARM, reverse-engineering, billing, content/marketing skills, etc. Don't import their conventions or add their tech.
- A skill never overrides `AGENTS.md`. In particular, don't let a skill push you to add new frameworks, ORMs, queues, or an external AI SDK — this project deliberately uses a provider-neutral gateway with a deterministic `fixture` adapter, and the job/queue system is implemented in-database.
- Do not modify files under `.agents/`.

## Gemini-specific guidance

- **Be literal about scope.** Implement what the active phase plan in `modules/backend/` asks for, and respect each plan's "Do not build yet" list. Do not add extra endpoints, providers, or infrastructure "while you're there".
- **Don't call external models or services from application code or tests.** AI behaviour goes through `ai/gateway.py` and the `fixture` provider; real-provider support would be a new adapter behind the same interface and requires explicit approval.
- **Prefer small, reviewable diffs.** Avoid wholesale rewrites or reformatting of files (models.py, services.py and schemas.py are large and shared). Edit surgically.
- **Don't regenerate or reorder migrations.** Add one new revision chained from the current head; never autogenerate-and-overwrite. Review any autogenerated migration by hand — it must match the model changes, use explicit constraint names, and downgrade cleanly.
- **Keep long outputs out of the repo.** Put scratch files, logs, and analysis in a temp directory, not in the project tree.
- **Keep the response honest and concise:** list files changed, checks run with results, and open risks. Do not claim tenant isolation, idempotency, or permission behaviour is covered unless a test demonstrates it.

## Pre-merge checklist (copy into your task list)

- [ ] Matches the owning module's existing pattern; routers thin, rules in services
- [ ] `tenant_id` filtering + cross-tenant test
- [ ] `require_permission` on every route; allowed and denied tests
- [ ] `If-Match`/`version` on mutable records; audit (+ outbox) in the same transaction
- [ ] Idempotency/duplicate-delivery handled and tested
- [ ] New Alembic revision; `upgrade head` and `downgrade base` pass
- [ ] `config.py` + `.env.example` + `README.md` updated if applicable
- [ ] `ruff`, `pytest`, `pyright` all pass (or gaps stated explicitly)
